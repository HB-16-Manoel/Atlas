# Journal Smart Scan — Phase 1 research and prototype

**Date:** 27 October 2026. **Scope:** GitHub `main` at `17508bbb`; experimental code only. No production Journal changes, database migrations, deployment, purchased services, or API credentials. Prices are USD list prices, subject to region, plan, taxes, and provider changes.

## Recommendation and decision gate

Prototype **Google Cloud Vision `DOCUMENT_TEXT_DETECTION`** first. Its API explicitly supports handwriting and returns pages, blocks, paragraphs, words, breaks, and confidence. The published ongoing price is the first 1,000 images/month free, then $1.50/1,000 images through 5 million; it fits a one-page-per-scan flow and needs no always-running OCR server. [Handwriting documentation](https://docs.cloud.google.com/vision/docs/handwriting) · [pricing](https://cloud.google.com/vision/pricing).

**This is a candidate, not an accuracy endorsement.** The actual recognition API could not be called: no Vision credential exists here, and enabling the API/billing is deferred. The prototype's upload, server request, response interpretation, editing, and error handling were tested with a fake provider. Before Phase 2, run a paid-tier-safe evaluation on representative, consented page photos, compare to a manually verified transcript, and accept/reject the provider based on WER, paragraph quality, hallucination/omission rate, and latency. If Vision struggles with cursive/corrections, compare Azure Read and a constrained vision model on the **same images**; route only troublesome scans to a second model if its measured gain warrants the cost.

## Cost model (monthly)

**Assumptions:** 1 image/page per scan, one API call, no retries or enhancements, USD, no tax. Google Vision's first 1,000 free units are available to the billing project as stated on its public page. AWS uses the Oregon example outside its temporary trial. Gemini estimate assumes 2,000 image/prompt input tokens and 400 output tokens per scan, paid API tier: `(2,000 × $0.10 + 400 × $0.40)/1,000,000 = $0.00036` per scan. **Token counts are unmeasured assumptions**, and model quality is unknown. Azure S0 estimate uses $1.50/1,000 paid pages without assuming F0 credits carry into S0.

| Scans/mo | Vision OCR verified rate | AWS Textract example | Azure Read S0 estimate | Gemini Flash-Lite illustrative |
|---:|---:|---:|---:|---:|
| 100 | $0 | $0.15 | $0.15 (F0 $0 within its 500-page cap) | $0.04 |
| 1,000 | $0 | $1.50 | $1.50 | $0.36 |
| 10,000 | $13.50 | $15.00 | $15.00 | $3.60 |
| 100,000 | $148.50 | $150.00 | $150.00 | $36.00 |

These are **API charges only**. Atlas can receive the photo in a short-lived authenticated Vercel function, call Vision server-side, and return text without storing the image. Using [Vercel's current fluid-compute prices](https://vercel.com/docs/functions/usage-and-pricing), an *illustrative* 0.2 s CPU + 2 s 0.25 GB provisioned memory in IAD costs roughly $0.0000086/scan; at 100,000 scans about **$0.86** plus up to roughly $0.06 invocation charges, before included allowances. Actual duration, concurrency, bandwidth, plan fees and request-size limits need a load test; Atlas's existing base Vercel/Supabase subscriptions are excluded. Retaining 1 MB image per scan for one month would be 0.1/1/10/100 GB at the four tiers; [Supabase Storage](https://supabase.com/docs/guides/storage/pricing) lists $0.0213/GB-month after the plan quota (100 GB on Pro, 1 GB on Free), so storage overage at 100k scans is $0 on Pro at exactly 100 GB but leaves no room for other assets; longer retention and download egress add cost. No image retention is needed to save editable text. One free user allowance is **not** the same as Vision's first 1,000 free project-wide units.

### Possible future allowance, without implementation

An initial idea is **5 free scans/account/month** and a higher, finite limit for a future paid tier (for example 100/month), plus rate limits per user and per IP and a project-wide cost alert. At 1,000 users all using five scans, Vision charge is `(5,000−1,000) × $0.0015 = $6/month`; at 10,000 such users, 50,000 scans cost $73.50. This excludes server traffic, repeated scans, account abuse, taxes, and support. Limits should be selected only after measured quality and average scans/user, with a clear fallback for manual Journal typing. No subscription or quota code is in this phase.

## Accuracy evidence and gaps

1. Local Tesseract baseline (`tesseract` default English) on two [public cursive line samples](https://github.com/arshjot/Handwritten-Text-Recognition/tree/master/samples) from the same writer (MIT repository; source examples, not user diary data). The reference was read manually from those images: 13 words. Tesseract required **10 word edits / 13 = 76.9% WER** using case/punctuation-insensitive matching. When the two images were composited into one page, Tesseract returned no text: **100% WER**; rotating that composite 8° and applying a strong synthetic lighting gradient also produced no text (both 100% WER). These transformations share the same writing and are not real angled/shadowed phone photos. This is one narrow negative baseline, not a representative corpus and not a Vision score.
2. Five Node tests passed: image type/size validation, mocked Vision request with server-only key, line/paragraph/punctuation handling, low-confidence marker, provider errors and HTTP review UI. A fake provider proves wiring, not handwriting recognition.
3. **Not tested with Vision:** clear handwriting, messy handwriting, cursive, actual multiparagraph diary pages, angled photos, low light, and crossed-out corrections. No Vision WER, speed, paragraph accuracy, or confident-error rate can be stated until a credential and consented benchmark exist. A paragraph fixture is synthetic, not an accuracy result.

For the decision gate, gather about 30–50 non-sensitive, consented one-page photos across writers/devices and all seven scenarios above. Keep manual ground truth in a private test set; calculate overall and per-scenario WER with `wer.mjs`, inspect punctuation/paragraph changes separately, time uploads and provider latency, and flag invented words/cross-outs. Include at least one Android camera sample. Set a target only after seeing pilot results; do not describe the system as reliable beforehand.

## Atlas integration plan (Phase 2, pending acceptance)

1. Add **Scan** within existing Journal for an authenticated account. Use camera capture (`accept=image/*`, `capture=environment`) plus ordinary upload; convert HEIC when needed. Preview/crop/rotate as appropriate, explain 5 MB limit, show progress and a retry that does not replace existing text.
2. Add an authenticated server endpoint using Supabase server session verification (`getUser`/claims) and an API key kept in server-only environment. Validate file signatures, dimensions and size; enforce per-user and abuse limits before provider calls, with budget alerts. Never put provider key or service-role secret in browser code. Consider EU processing and privacy terms before sending personal pages.
3. Show original photo side-by-side (stacked on mobile) with editable transcription. Mark uncertain words, never auto-save OCR text. Let user confirm corrections and choose date; warn before replacing a non-empty current entry. Historical Journal entries are read-only today, so don't silently bypass that rule.
4. On explicit confirmation, use the existing `JournalEntry` (`date`, `text`, `mood`, `energy`, `rating`) and `setJournalEntries`/`useAtlasData` cloud repository. Current cloud `journal_entries` has one entry per user/date with revision and owner-scoped RLS; normal sync/persistence handles it. Do not add a second text database or merge into an unsynced entry. Handle revision conflicts/account switches and never present another account's scanned draft.
5. Original image retention should default **off**. If user opts in later, add a private Supabase Storage bucket with per-user path/RLS, deletion handling, size and retention policy; no public image URL. The current experiment stores no images, has no production endpoint, and no DB migration.
